# CREWS - 소모임 관리 및 금융 서비스 플랫폼

[![GitHub Repository](https://img.shields.io/badge/GitHub-Repository-blue?logo=github)](https://github.com/dlaudfuf33/CREWS)
<img width="635" height="240" alt="이명렬-포트폴리오 2 0" src="https://github.com/user-attachments/assets/888ce682-4e57-40ec-93c4-341919932b97" />

CREWS는 코어 뱅킹 기반의 금융 서비스를 포함한 소모임 관리 플랫폼입니다. 사용자는 모임 일정, 자산, 회비 등을 통합 관리하며, 금융 서비스를 활용한 다양한 기능을 제공받을 수 있습니다.

기존 소모임 운영은 회비 납부, 추적, 독촉, 회비 소비 내역 확인 등 여러 과정이 번거롭고 복잡하며, 소모임 플랫폼과 은행 앱 등 다양한 서비스를 번갈아 사용하는 불편함이 있었습니다.
CREWS는 이러한 문제를 해결하기 위해 소모임 운영과 회비 관리의 디지털화를 목표로, 한 플랫폼에서 모든 과정을 쉽고 간편하게 처리할 수 있도록 설계 및 개발되었습니다.
<br>

## 1. 프로젝트 목표

기존 소모임 운영은 회비 납부 추적, 독촉, 소비 내역 확인 등 여러 과정이 수작업으로 이루어져 비효율적이었습니다. 또한, 소모임 관리 앱과 은행 앱을 번갈아 사용해야 하는 불편함이 있었습니다.

CREWS는 이러한 문제들을 **디지털화**하여 해결하고, **하나의 플랫폼에서 모든 소모임 활동과 금융 관리를 완결**할 수 있는 통합적인 사용자 경험을 제공하는 것을 목표로 합니다.

<br>

## 2. 주요 기능

- **통합 대시보드:** 모임의 자산, 다가오는 일정, 회비 납부 현황을 한눈에 파악합니다.
- **회비 관리 자동화:** 정기 회비 납부 요청 및 알림을 자동화하고, 납부 내역을 실시간으로 추적합니다.
- **모임 통장 서비스:** 플랫폼 내에서 간편하게 모임 통장을 개설하고, 회비 이체 및 자산 관리를 수행합니다.
- **활동 및 정산 관리:** 모임 활동 내역을 기록하고, 비용을 투명하게 정산 및 관리합니다.
- **보안:** JWT 및 API Key 기반의 강력한 인증/인가 체계를 통해 사용자의 자산을 안전하게 보호합니다.

<br>

## 3. 시스템 아키텍처

CREWS는 서비스의 역할과 책임을 명확히 분리하기 위해 **서비스 지향 아키텍처(SOA)**를 채택했습니다. 비금융 서비스와 핵심 금융 기능을 독립된 서버로 구축하여 시스템의 안정성, 확장성, 유지보수성을 극대화했습니다.

![mama](https://github.com/user-attachments/assets/bdb54032-e7c4-4390-b4ae-6b7694ee4bb1)


- **Service Server (Spring Boot):** 사용자 인증/인가, 모임 관리 등 핵심 비즈니스 로직을 담당합니다.
- **Core Banking Server (Spring Boot):** 계좌 관리, 이체 처리 등 민감한 금융 기능을 독립적으로 수행하는 BaaS(Banking as a Service) 서버입니다.
- **AWS SQS:** 결제와 같이 트래픽이 집중될 수 있는 작업을 비동기 메시지 큐로 처리하여 시스템 부하를 분산시키고 안정성을 보장합니다.
- **Resilience4j Circuit Breaker:** 서버 간 통신 장애가 발생할 경우, 장애 전파를 막고 시스템이 안정적으로 대체 동작을 수행하도록 합니다.

## 5. 핵심 문제 해결: 동시성 제어

금융 시스템의 신뢰도를 좌우하는 데이터 정합성 문제를 해결하는 것은 본 프로젝트의 가장 중요한 과제였습니다.

### 문제 상황
여러 사용자가 동시에 특정 계좌에서 출금을 시도할 경우, **경쟁 상태(Race Condition)**가 발생하여 잔액이 잘못 계산되는 문제가 있었습니다. 예를 들어, 잔액 10,000원인 계좌에서 두 스레드가 동시에 1,000원을 출금하면, 두 스레드 모두 10,000원을 조회한 후 연산을 수행하여 최종 잔액이 8,000원이 아닌 9,000원으로 남게 됩니다.

### 해결 과정
1.  **다양한 동시성 제어 모델 검토:** `낙관적 락`, `비관적 락`, `작업 큐`, `분산 락`의 장단점을 분석했습니다.
2.  **`비관적 락` 채택:** 충돌이 빈번한 쓰기 작업(이체)의 특성을 고려할 때, 데이터 정합성을 가장 확실하게 보장하는 `비관적 락`이 최적의 해결책이라고 판단했습니다.
3.  **최적화 및 데드락 방지:**
    - **선별적 락 적용:** 데이터 수정이 발생하는 쓰기 작업에만 락을 적용하고, 단순 조회는 허용하여 성능 저하를 최소화했습니다.
    - **데드락 방지:** 트랜잭션 내에서 항상 **`출금 계좌 → 입금 계좌`** 순으로 리소스에 접근하도록 표준화하여 데드락 발생을 원천 차단했습니다.
4.  **성능 검증:** `ExecutorService`와 `CyclicBarrier`를 사용하여 1,000개의 동시 요청 시나리오를 테스트했으며, 모든 요청 후에도 데이터 정합성이 완벽하게 유지됨을 검증했습니다.
